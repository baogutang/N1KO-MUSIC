### 致命-1 Jellyfin/Emby adapter userId is set to the access token and never corrected

**位置**: `frontend/src/api/index.ts:34` · **维度**: API 适配器

**问题**: createAdapter() constructs JellyfinAdapter/EmbyAdapter with `userId: config.token` (lines 34 and 41), with a comment claiming it will be updated at init — but nothing ever updates it. ServerConfig (frontend/src/api/types.ts) has no userId field, and serverStore.updateServerAuth (frontend/src/store/serverStore.ts:100) explicitly discards its userId argument (`_userId`). Worse, the login flow in frontend/src/pages/Login.tsx builds a correct adapter with result.userId (line 103-108) but then immediately calls activateServer(serverId) (line 118), which calls createAdapter() and setActiveAdapter() again, replacing the correct adapter with the broken one whose userId is the token. The same happens on every page refresh via onRehydrateStorage (serverStore.ts:122-127). The bogus userId is then used in /Users/{userId}/PlayedItems, /Users/{userId}/FavoriteItems, every UserId query param on /Items, /Artists, /Playlists, and in the stream URL (jellyfin.ts:245).

**用户可见的表现**: User logs into a Jellyfin server: the moment activateServer runs (immediately after login, and again on every refresh), all requests carry UserId=<access token>. Favoriting a song (star -> POST /Users/<token>/FavoriteItems/<id>) fails, scrobbling fails, UserData-dependent state (favorites, play counts) is wrong or requests 400 with 'User not found', despite login having succeeded.

**修复建议**: Add a `userId` field to ServerConfig, persist result.userId in updateServerAuth/addServer for jellyfin/emby, and pass config.userId in createAdapter instead of config.token.

**验证者补充**: Finding is accurate as stated, with two minor precisions: (a) scrobble only hits /Users/{userId}/PlayedItems when submission=true; the submission=false branch posts to /Sessions/Playing, which does not use userId and is unaffected; (b) whether the UserId query param on /Items//Artists causes a hard 400 or just wrong/empty UserData depends on Jellyfin server version, but the /Users/{token}/... path-based endpoints (favorite, played) definitively target a nonexistent user. Also note Login.tsx never even passes userId to updateServerAuth for jellyfin/emby — the discarded `_userId` parameter is dead code on top of the missing ServerConfig field.

### 高-1 Toggling favorite (star) on the playing song restarts it from the beginning

**位置**: `frontend/src/hooks/useAudioEngine.ts:631` · **维度**: 播放引擎

**问题**: The core load effect depends on the `currentSong` object reference (line 631), and its React cleanup (lines 623-629) calls `cleanupPrev()` and nulls it before the effect body re-runs. The skip guard at line 205 requires `loadedKey === currentKey && cleanupPrev`, but `cleanupPrev` is always null after a dependency-change cleanup, so the guard can never skip on a same-song re-run. The body then takes the non-first-play path (lines 217-224): `audioEl.pause()`, `audioEl.src = ''`, store `currentTime` reset to 0 (line 227), and a full debounced reload of the same song from position 0. `updateCurrentSong()` in playerStore.ts (line 375-379) creates a new `currentSong` object with the same id, which is exactly this trigger. The same path fires when `isConnected` flickers false->true mid-song (line 197 early-returns while disconnected, cleanup already nulled `cleanupPrev`, reconnect does a full reload from 0). This is a live remnant of the v1.2.2-v1.2.5 'unexpected restart from beginning' bug family.

**用户可见的表现**: Play a song and let it reach e.g. 2:30, then click the heart/star button in PlayerBar (PlayerBar.tsx:177 calls `updateCurrentSong({ starred: ... })` on success) or FullscreenPlayer (FullscreenPlayer.tsx:225). The audio stops, the progress bar jumps to 0:00, and after ~120ms the same track reloads and plays from the beginning. Same restart happens if the server connection state briefly drops and reconnects mid-song.

**修复建议**: Depend only on `currentSong?.id` (not the object) in the effect, or make the `loadedKey === currentKey` branch re-attach listeners without touching `audioEl.src`/currentTime when only the reference (or connection state) changed.

**验证者补充**: The bug is exactly as described; the only correction is a file path: the star button lives in frontend/src/components/layout/PlayerBar.tsx (line 177), not components/player/PlayerBar.tsx. Toggling favorite on the playing song (or an isConnected flicker) triggers a dependency-change cleanup that nulls cleanupPrev, defeating the same-key skip guard at line 205 and causing a full pause/src=''/currentTime=0 reload of the same song from position 0.

### 高-2 Plays are never submitted to the server: scrobble is only ever called with submission=false

**位置**: `frontend/src/hooks/useAudioEngine.ts:586` · **维度**: 播放引擎

**问题**: The only scrobble call in the app is `getAdapter().scrobble(capturedSongId, false)` at load time. `submission=false` is the Subsonic 'now playing' notification (subsonic.ts:388-390) and the Jellyfin 'Sessions/Playing' report (jellyfin.ts:281-288); neither marks the item as played. `submission=true` (Subsonic scrobble submission / Jellyfin `PlayedItems` POST, jellyfin.ts:280) is never invoked anywhere in the codebase, and there is no completion/threshold logic (e.g. after 50% or 4 minutes) to submit it. Additionally the call fires immediately on load, before a single second has played.

**用户可见的表现**: User listens to full albums through the app for weeks: Navidrome/Jellyfin play counts stay at 0, 'Most played'/'Recently played' server views never update, and Last.fm scrobbling configured on the Navidrome server never receives any scrobbles, because no submission=true request is ever sent.

**修复建议**: Keep the now-playing call at load, and add a one-shot `scrobble(id, true)` when the track passes the standard threshold (min(duration/2, 4min)) or on the `ended` event.

### 高-3 Subsonic getLyrics reads non-existent response keys 'o3icsList'/'o3ics' — lyrics never load

**位置**: `frontend/src/api/adapters/subsonic.ts:346` · **维度**: API 适配器

The first branch therefore always yields an empty list and falls through; the legacy branch always finds `raw` undefined and returns null. Note the same corrupted rename hit setLyrics (line 602, param `o3ics`) and useServerQueries query keys, though those are non-standard endpoints.

**用户可见的表现**: User connected to Navidrome plays a song that has embedded/synced lyrics; the server returns them correctly under `lyricsList`, but the app parses `o3icsList`, gets nothing, and the lyrics panel permanently shows empty for every song on Subsonic/Navidrome servers.

**修复建议**: Rename `o3icsList` back to `lyricsList` and `o3ics` back to `lyrics` in the two response parsers (and verify what the custom /setLyrics endpoint actually expects as its parameter name).

### 高-4 Persisted lyric cache keyed by songId only — collides across servers and suppresses correct lyrics

**位置**: `frontend/src/store/o3icCacheStore.ts:44` · **维度**: 状态与缓存

**问题**: The lyric cache (the live store — SongDetail.tsx:457 writes via saveLyrics, useServerQueries.ts:138 reads) persists entries under the bare songId with no server scoping, while the app explicitly supports multiple servers (serverStore.ts servers[] + activateServer). **验证者补充**: Finding is accurate as stated. One minor precision: within the Subsonic family, realistic id collisions apply to plain Subsonic/Airsonic (sequential numeric ids); Navidrome, Jellyfin, and Emby use long hashed/GUID ids, making cross-server collisions unlikely there — but the app explicitly supports the 'subsonic' server type, so the scenario stands. Independently of collisions, the unscoped cache also survives server removal indefinitely with no invalidation path.

### 高-5 Switching servers never invalidates React Query cache — previous server's library shown and old song IDs sent to new server

**位置**: `frontend/src/store/serverStore.ts:69` · **维度**: 状态与缓存

**问题**: activateServer() only swaps the adapter (createAdapter/setActiveAdapter) and sets flags; it never touches the QueryClient. Every query key in useServerQueries.ts (queryKeys at lines 26-41: songs, albums, artists, playlists, starred, o3ics, search, infinite lists) omits the server id, and staleTime is 5-30 minutes, so after an in-session server switch all mounted pages keep rendering the previous server's data and will not refetch (data is still "fresh" under the unchanged key). **用户可见的表现**: User is on the Library page connected to server A, opens the sidebar server dropdown and picks server B. The toast says switched, but the song/album lists still show server A's library. **修复建议**: Call queryClient.clear() (or queryClient.invalidateQueries()) on activateServer/disconnect, or include activeServerId in every query key.

### 高-8 Publicly-known fallback JWT secret used whenever NODE_ENV is not exactly 'production'

**位置**: `backend/src/middleware/auth.ts:15` · **维度**: 后端

**问题**: The guard at line 7 only throws when NODE_ENV === 'production'. In every other case (NODE_ENV unset, 'prod', 'staging' — the common state for a NAS user who just runs `npm start` or a Docker container without setting NODE_ENV), the server silently falls back to the hardcoded secret 'msp-dev-secret-change-in-production', which is committed to the public repo. All tokens are HMAC-signed with this known secret, so anyone who can reach the backend can mint a valid 30-day token for any userId/username.

**用户可见的表现**: Backend deployed on a LAN/NAS without NODE_ENV=production. An attacker (or any curious user on the network) signs {userId: '<victim-uuid>', username: 'victim'} with the string from the repo, sends `Authorization: Bearer <forged>` to DELETE /api/playlists/:id or DELETE /api/stats/history, and passes authMiddleware — full read/write/delete access to every user's playlists and play history. UserIds are also returned verbatim in login/register responses, and even without a known uuid the attacker can enumerate via forged tokens.

**修复建议**: Refuse to start (or auto-generate and persist a random secret in DATA_DIR) whenever JWT_SECRET is unset, regardless of NODE_ENV; never fall back to a compile-time constant.

### 高-10 Lyric auto-scroll disables itself: programmatic smooth scroll is counted as manual scrolling

**位置**: `frontend/src/components/player/LyricDisplay.tsx:66` · **维度**: 交互体验

**问题**: The manual-scroll detector (LyricDisplay.tsx:60-73) listens to the container's 'scroll' event and stamps lastManualScrollRef on every event. But scrollToActive() itself scrolls the same container with behavior:'smooth' (lines 92-95), which fires a burst of scroll events, so every successful auto-scroll arms the 3-second lock (checked at line 79). Any lyric line that starts less than ~3s after the previous auto-scroll finishes is never scrolled to. There is no flag distinguishing programmatic scrolls from user scrolls.

**用户可见的表现**: Open the fullscreen player on a normal song where lyric lines advance every 2-3 seconds: the highlighted line scrolls once, then the next several highlighted lines drift down off-center (and eventually out of view) because auto-scroll is locked out by its own scroll events; every ~3.5s the view suddenly jumps to re-center. Auto-scroll only works smoothly for songs with >3s gaps between lines.

**修复建议**: Set a suppress flag (or record the target scrollTop) before calling container.scrollTo() and ignore scroll events until the animation settles near the target (or use a scrollend listener / short timeout), only stamping lastManualScrollRef for events not caused by scrollToActive.

**验证者补充**: Programmatic smooth scrolls from scrollToActive() fire scroll events that stamp lastManualScrollRef, arming the 3-second manual-scroll lock after every auto-scroll. However, auto-scroll is not permanently disabled: skipped scrolls emit no events, so the lock expires ~3 s after the previous smooth scroll finishes. For songs with lines every <3 s the real behavior is alternating skip-then-jump — some highlighted lines are never scrolled to and drift off-center, then the view jumps to re-center on a later index change — rather than total self-disablement. Smooth continuous following only works when gaps between lines exceed ~3 s.

## 中（medium）· 17 项

### 中-1 Shuffle mode ignores repeatMode: repeat-one does not repeat, repeat-off loops the queue forever

**位置**: `frontend/src/store/playerStore.ts:149` · **维度**: 播放引擎

**问题**: In `next()`, the `if (shuffle)` branch (lines 149-152) runs before any repeatMode check and always computes `(currentShufflePos + 1) % shuffledIndexes.length`. Consequences: (1) with shuffle on and repeatMode 'one', a track that ends advances to the next shuffled track instead of repeating (the `repeatMode === 'one'` branch at line 153 is unreachable); (2) with shuffle on and repeatMode 'none', reaching the last shuffled position wraps modulo back to the start, so the 'stop at end of queue' branch (lines 159-161) is also unreachable and playback loops the queue indefinitely. `prev()` has the mirrored wrap at lines 200-204. `onEnded` in useAudioEngine.ts (line 391) routes natural track endings through this same `next()`.

**用户可见的表现**: Enable shuffle, set repeat to 'one', play a song: when it ends it jumps to a different random song instead of repeating. Enable shuffle with repeat off and play a 10-song queue overnight: instead of stopping after the 10th song, the queue re-loops endlessly.

**修复建议**: Check `repeatMode === 'one'` before the shuffle branch, and inside the shuffle branch stop (set isPlaying false) when `currentShufflePos` is the last position and repeatMode !== 'all'.

### 中-2 Shuffle branch of next() ignores repeat-one mode

**位置**: `frontend/src/store/playerStore.ts:149` · **维度**: 队列逻辑

**问题**: In next(), the `if (shuffle)` branch is checked before `repeatMode === 'one'` (line 153), so when shuffle is enabled repeat-one is never honored. Since useAudioEngine.ts calls store.next() on natural song end (onEnded, useAudioEngine.ts:391), a song set to repeat-one will not repeat while shuffle is on.

**用户可见的表现**: User enables shuffle and sets repeat mode to 'one', song A finishes playing -> instead of A repeating, the player advances to the next song in the shuffled order.

**修复建议**: Check `repeatMode === 'one'` before the shuffle branch in next() (prev() ordering can stay, since explicit prev should navigate even in repeat-one).

### 中-3 Shuffle playback never stops: wraps past end even with repeat off

**位置**: `frontend/src/store/playerStore.ts:151` · **维度**: 队列逻辑

**问题**: In shuffle mode next() computes `(currentShufflePos + 1) % shuffledIndexes.length`, unconditionally wrapping to the start of the shuffled order regardless of repeatMode. The non-shuffle path correctly stops (`set({ isPlaying: false })`, lines 159-161) when repeatMode is 'none' and the queue is exhausted. With shuffle on, playback loops the queue forever.

**用户可见的表现**: Shuffle on, repeat mode 'none', queue of 10 songs: after the 10th shuffled song ends, playback jumps back to the first shuffled song and keeps playing indefinitely instead of stopping like it does without shuffle.

**修复建议**: In the shuffle branch, if `currentShufflePos === shuffledIndexes.length - 1` and repeatMode !== 'all', stop playback instead of wrapping.

### 中-4 "Play next" inserts at a random position when shuffle is on

**位置**: `frontend/src/store/playerStore.ts:254` · **维度**: 队列逻辑

**问题**: addToQueue(songs, 'next') (invoked by playNextInQueue, frontend/src/utils/playActions.ts:29, wired to the SongList '下一首播放' action) inserts the songs at queueIndex+1 in the queue array, but when shuffle is active it then regenerates the entire shuffledIndexes with generateShuffledIndexes (lines 254-256), which places every non-current song at a random position. Since next() follows shuffledIndexes, the song the user asked to play next actually plays at an arbitrary future point.

**用户可见的表现**: Shuffle enabled, user clicks 'play next' on song X in a 50-song queue -> the current song ends and a random other song plays; X may not come up until dozens of songs later.

**修复建议**: When shuffle is on, splice the new songs' queue indexes into shuffledIndexes immediately after the current song's shuffle position (remapping existing indexes >= insertAt by +songs.length) instead of regenerating the whole order.

**验证者补充**: The finding is accurate as stated. One additional consequence worth noting: regenerating shuffledIndexes in addToQueue also resets the current position in the shuffle cycle to 0, discarding which songs were already played this cycle, so previously played songs can repeat before the shuffle order completes. Fix direction: when shuffle is on and position is 'next', splice the new indexes into shuffledIndexes immediately after the current song's shuffle position (remapping existing indexes >= insertAt by +songs.length) instead of regenerating.

### 中-5 Removing or reordering any queue item re-shuffles the entire upcoming order

**位置**: `frontend/src/store/playerStore.ts:303` · **维度**: 队列逻辑

**问题**: removeFromQueue (lines 296-305) and reorderQueue (lines 335-337) call generateShuffledIndexes whenever shuffle is on. That resets the shuffle traversal position to 0 (current song first) and randomly reorders all other songs, so songs already played in the current shuffle pass re-enter the upcoming rotation and the previously shown 'coming up' order is discarded. Removing one unrelated song should not change which songs come next or cause replays before unplayed songs get their turn.

**用户可见的表现**: Shuffle on, 40 of 50 songs already played in this pass; user removes one already-played song from the queue drawer -> the next tracks are freshly re-randomized and several of the 40 already-played songs play again before the 10 remaining unplayed ones.

**修复建议**: Instead of regenerating, remap the existing shuffledIndexes: for removal, drop the removed index and decrement indexes greater than it; for reorder, translate each stored index through the same from->to mapping applied to the queue.

**验证者补充**: removeFromQueue (frontend/src/store/playerStore.ts lines 296-298 and 303-305) and reorderQueue (lines 335-337) call generateShuffledIndexes whenever shuffle is on. That function builds a fresh random permutation with the current song at position 0; since next() derives the traversal position from shuffledIndexes.indexOf(queueIndex), the effective position resets to 0 and all other songs (played and unplayed alike) are randomly reordered behind it. Removing or reordering any queue item therefore discards the previous upcoming order and lets already-played songs replay before unplayed ones. The same pattern also exists in addToQueue (lines 254-262), which the original finding did not mention. A lossless remap of the existing permutation (drop the removed index, shift the rest) would avoid this.

Correction to the scenario: no shipped UI chart is affected — the frontend Stats page builds its charts from localStorage in the user's local timezone and never calls /api/stats/summary (scrobbles also go to the media server, not this backend), so the misattribution exists only in the API response for external/future consumers. Note also that adding 'localtime' would use the server's timezone, not each user's; a correct fix needs a client-supplied timezone offset.

### 低-8 Registration check-then-insert race across async bcrypt returns 500 instead of 409

**位置**: `backend/src/routes/auth.ts:25` · **维度**: 后端

**问题**: The duplicate-username SELECT (line 20) and the INSERT (line 27) are separated by `await bcrypt.hash(password, 10)` (~50–100ms). Two concurrent register requests for the same username can both pass the existence check; the second INSERT then violates the UNIQUE constraint on users.username, throws, and is caught by the generic catch, returning a 500 'Internal server error' instead of the intended 409 'Username already exists'.

**用户可见的表现**: User double-clicks the register button (or two devices submit the same username simultaneously). One request succeeds; the other shows a generic server error instead of 'Username already exists', and the client may treat registration as failed even though the account now exists.

**修复建议**: Drop the pre-check and catch the SQLITE_CONSTRAINT_UNIQUE error from the INSERT, mapping it to 409.

### 低-9 Password change does not invalidate previously issued 30-day tokens

**位置**: `backend/src/middleware/auth.ts:47` · **维度**: 后端

**问题**: Tokens are stateless JWTs valid for 30 days, and change-password (backend/src/routes/auth.ts:83) only rewrites the bcrypt hash — nothing ties token validity to the current credential (no token-version claim, no iat-vs-passwordChangedAt check, no denylist). Every token issued before the password change remains fully valid until its natural expiry.

**用户可见的表现**: A user's token is leaked (shared device, logged request). The user changes their password expecting to lock the attacker out, but the attacker's old Bearer token keeps working against all /api endpoints for up to 30 more days.

**修复建议**: Store a per-user tokenVersion (or passwordChangedAt) and embed/check it in the JWT payload during authMiddleware, bumping it on password change.
